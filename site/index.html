§1 · field rule

Found a tick? Don't squeeze it.
Found a cook.pth? Don't start Python.

LiteLLM 1.107.0 (PyPI and Docker, 21 Oct 2026) put three files at the top of site-packages. One of them, cook.pth, is 12 bytes: import cook. Python's site module runs every .pth line that starts with import, on every interpreter start, and sitecustomize.py is imported right after. Nothing has to import litellm. So the first thing most people reach for runs the stealer again.

$ pip show litellm
  1. python starts
  2. site.py reads cook.pth
  3. import cook
  4. stealer runs again
$ tickcheck
  1. reads files
  2. hashes, RECORDs, transcripts
  3. BAD · nothing ran

sha256 of those 12 bytes: 7f191632…2bdb, as published in BerriAI/litellm#47826. The vendor's own notice: "Don't start with pip install. Any Python start in the affected environment runs cook.pth and sitecustomize.py again." (docs.litellm.ai)

§2 · key to the verdicts

A dichotomous key, not a vibe.

Every hook is keyed out the same way, from the file alone. Pick a specimen from the demo drawer to see the route it takes.

  1. 1aA .pth whose lines are all paths (none starts with import)nothing runs · not listed
  2. 1bA .pth line starts with import + space/tab, or the file is sitecustomize / usercustomize→ 2
  3. 2aIts sha256, or its package's name + version, is in the IOC feedBAD
  4. 2bNot in the feed→ 3
  5. 3aIn no installed package's RECORD (dropped there, not installed)→ 4
  6. 3bListed in a RECORD→ 5
  7. 4aPayload signals: encoded blob → exec, network, fork/setsid, credential pathsSUSPECT
  8. 4bPlain codeREVIEW
  9. 5aThe RECORD sha256 differs from the file on diskSUSPECT
  10. 5bHash matches→ 6
  11. 6aA known pattern from its own package: setuptools shim, editable install, -nspkg, pywin32, coverageOK
  12. 6bPayload signals, or a name unrelated to its package (litellm → cook.pth)SUSPECT
  13. 6cOtherwiseREVIEW

The signals are text matches; nothing is decoded or run. A known name hiding a payload (a _virtualenv.py that calls subprocess) still keys out as SUSPECT. Full rules and the IOC feed format: docs § verdicts.

§3 · collection record

Who put it there?

Agents make venvs and pip install on their own, often mid-task after a ModuleNotFoundError. For every BAD or SUSPECT hook, tickcheck reads Claude Code, Codex, OpenCode and Gemini CLI transcripts and your shell history as text to find the command that installed its package.

It also reads the package's own INSTALLER and RECORD time. In the demo below, the LiteLLM proxy env was set up by a Claude Code session and the worktree hook came from a Codex pip install.

§4 · into the vial

Pull it straight out.

tickcheck pull moves each BAD hook, the module its .pth line loads, and their __pycache__ copies into ~/.tickcheck/quarantine/<time>/, with a manifest of every original path and sha256. tickcheck restore <dir> puts them back. Python is never started, before or after.

$ tickcheck pull --demo --yes
tickcheck pull · 3 files + 2 compiled copies from 1 environment · Python was never started

  ~/proj/agent-proxy/.venv
    cook.pth  cook.py  cook.cpython-312.pyc  sitecustomize.py  sitecustomize.cpython-312.pyc

moved 3 files + 2 compiled copies → ~/.tickcheck/quarantine/20261022-104512/
  manifest.json lists every file and its sha256; `tickcheck restore ~/.tickcheck/quarantine/20261022-104512` puts them back

re-check: 0 BAD hooks left in 7 environments.
note: litellm 1.107.0 (litellm-2026-10-21) is still installed in ~/proj/agent-proxy/.venv: rebuild that env, don't run its pip.
The next Python start won't run them. If they ever ran with network access, rotate what this machine could read.

Pulling doesn't un-steal anything. On a BAD hit tickcheck lists the credential files of the kinds the stealer targets that exist on the machine. It never opens them. For rotation, keyroll finds every copy of an AI key.

§5 · localities searched

Every environment, not just the one you remember.

  • Project venvsany folder with pyvenv.cfg under ~, including .venv inside agent worktrees (.claude/worktrees, .codex)
  • Tool envspipx venvs, uv tools, uvx environments in the uv cache, pre-commit envs
  • Interpreterspyenv versions, uv-managed Pythons, conda / mamba / miniforge envs
  • User site and system~/.local, /usr/lib/python3.X (Debian's sitecustomize), /usr/local, Homebrew, Python.org framework, C:\Python3X, AppData
  • Package cachesuv, pip and poetry caches holding a poisoned dist or wheel, one uv sync away from an env
  • The host/tmp markers (.pc_once_*, remote_code_loader.lock) and, on Linux, any process holding the lock (read from /proc; nothing is killed)
  • Containers and CIdocker export a container, untar it, tickcheck --root rootfs. In CI, the exit code (4 BAD, 3 SUSPECT) fails the job.
  • Your own feed--ioc incident.json adds hashes, dists and host markers for the next incident

§7 · install

One binary. Read it before you pipe it.

# Linux / macOS: downloads the release for this machine and checks it against checksums.txt
curl -fsSL https://blackman99.github.io/tickcheck/install.sh | sh
# or, with Go
go install github.com/Blackman99/tickcheck/cmd/tickcheck@latest
# Windows: tickcheck_windows_amd64.zip from the releases page

tickcheck --demo        # a generated home with a defanged LiteLLM drop
tickcheck               # your machine; exit 4 = BAD, 3 = SUSPECT
tickcheck --root /srv   # one folder, a CI workspace, an unpacked container
